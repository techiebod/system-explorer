# The two-guest estate harness

Gate 4's last clause is *a two-guest estate renders one coherent view with
reach and coverage stated*, and standing rule 3 puts federation tests on
**two lab guests as two sites**. This is what judges it, and it lives here
so the gate rests on something anybody can re-run rather than on a
transcript.

Everything below runs the **real** binaries on **real** guests: the Go
collector reads a real kernel, the Go collator applies and dials, and the
Python hub promotes. Nothing is faked, which is the whole point — the CI
suites already prove the protocol against generated bytes, and what they
cannot prove is a real network between two machines.

## What the guests need

`test/vm-lab` brings them up; this harness assumes they are already
running and does not create them. Ship to each guest's `~/se-lab`:

- `se-collate` and the collectors, built for the guest:
  `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o …`
- the hub modules as a package named `sehub` — they are stdlib-only, so a
  guest needs no dependencies at all
- `run_estate.py` and `run_peer.py` from this directory

## One estate over two guests

```sh
# on the guest that will hold the hub
python3 run_estate.py hub 9500 2

# on each guest, including the hub's own
python3 run_estate.py collator lab-b 127.0.0.1:9500
python3 run_estate.py collator lab-a <hub-guest-ip>:9500
```

The hub prints the promoted view: every row, the reach state per host,
coverage as identities, and the estate's answer to *are all hosts up to
date*.

## Two guests as two sites

Which side dials is a **deployment fact stated per pair**, never assumed
symmetric — a site behind NAT can only originate — so the two modes are
separate commands rather than one symmetric one:

```sh
python3 run_peer.py serve site-b 9401              # the member that ACCEPTS
python3 run_peer.py dial  site-a <ip>:9401         # the member that ORIGINATES
```

Add `--divergent` to the serving side to exercise the refusal path: it
holds a different intent revision, and the dial must be refused with
`intent-mismatch` naming both hashes.

## What it found, 2026-08-20

Two things no generated fixture produced, both recorded because a harness
that only confirms what its author expected is the defect this project is
named after.

**A booted generation with no configuration revision.** On the NixOS
guest, generation 1 is booted and current and carries no revision, while
generation 4 carries one and is neither. The answer refuses to report a
revision the host is not running, and says so per host.

**Two different silences behind one count.** `lab-a` read its generations
and none was booted-with-a-revision; `lab-b` runs no NixOS generations at
all. The answer reported "2 of 2 declared hosts could not answer" and
named neither. Both are named now, and a dark host is still owed its
reason — going away and having had nothing to say are different facts.
