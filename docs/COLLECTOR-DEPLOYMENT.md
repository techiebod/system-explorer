# Deploying collectors

**What a deployment must write so a host's collector fleet is defined,
credentialled and privileged — and what it must not.**

Status: specification. Nothing here is built.

---

## The split this makes possible

Today one agent process holds, simultaneously, the `docker` group,
`CAP_NET_ADMIN`, disk access, and every application API key the host is
configured with. Every adapter runs inside that. The blast radius is the union
of what any adapter needs.

Collectors as separate programs change that, and **the change lands entirely in
the deployment**:

| | today | with per-collector deployment |
|---|---|---|
| docker socket | the whole agent | the docker collector |
| `CAP_NET_ADMIN` | the whole agent | the nftables collector |
| disk / SMART | the whole agent | the disk collector |
| application keys | the whole agent | one key per collector, and no collector sees another's |
| the service | — | **none of the above** |

The service holds watches, the hub connection and a socket. It reads no
device, holds no key, and needs no capability. That is worth more than the
memory.

## Two gates, and they answer different questions

**The deployment decides what is installed and what it may reach. The probe
decides what actually runs.**

Deployment is about *authority* — this host's docker collector exists, and here
is the socket and the group it may use. Probing is about *applicability* — the
socket is not there today, so it declines with a reason.

Conflating them is how you get either a collector with credentials it never
needed, or a host that silently observes nothing because a probe failed at boot
and nobody re-ran it. Keep them separate: a collector may be installed and
decline; it may never run without being installed.

## 1. The collector manifest

The deployment writes one file. Generated by Nix, atomic, world-readable, and
containing **no secrets**.

```
/etc/system-explorer/collectors.json
```

```json
{
  "schema": 1,
  "collectors": [
    { "name": "units",
      "exec": "/nix/store/xxxx-se-collect-units/bin/se-collect-units" },

    { "name": "docker",
      "exec": "/nix/store/yyyy-se-collect-docker/bin/se-collect-docker",
      "environment": { "SE_DOCKER_SOCKET": "/var/run/docker.sock" },
      "supplementaryGroups": [ "docker" ] },

    { "name": "nftables",
      "exec": "/nix/store/zzzz-se-collect-nft/bin/se-collect-nft",
      "capabilities": [ "CAP_NET_ADMIN" ] },

    { "name": "servarr",
      "exec": "/nix/store/wwww-se-collect-servarr/bin/se-collect-servarr",
      "environment": { "SE_SERVARR_INSTANCES": "radarr,sonarr" },
      "environmentFile": "/run/secrets/se-servarr" }
  ]
}
```

| Member | Required | Meaning |
|---|---|---|
| `name` | yes | The collector's identity. Unique per host. Appears in error messages, in the budget, and in any decline. |
| `exec` | yes | Absolute path to the executable. A store path in practice, so the fleet is pinned by the closure. |
| `environment` | no | Non-secret configuration, inline. Socket paths, endpoints, instance lists. |
| `environmentFile` | no | Path to a file of `KEY=value` lines, read by the **service** at invocation and passed only to this collector. **Never a store path.** |
| `supplementaryGroups` | no | Groups this collector's process joins. Nothing else on the host gains them. |
| `capabilities` | no | Capabilities in its bounding set. Empty unless named. |
| `readPaths` | no | Paths this collector may read, if the service confines it. See §4. |

## 2. What must never be in it

- **Secret values.** `environmentFile` names a path; the deployment materialises
  the file at activation from `sops-nix` or equivalent. A key interpolated into
  the manifest is a key in `/nix/store`, which is world-readable and goes to a
  binary cache.
- **A default path for anything the estate may not have.** The existing
  `deploymentReceipts` option has no default for exactly this reason: an agent
  inventing a path, finding nothing, and reporting the nothing as a fact is the
  failure this product exists to prevent. Same rule here.
- **Collectors the host has no authority for.** Installing the docker collector
  without the group is not "it will decline gracefully" — it is a collector that
  fails for a reason indistinguishable from docker being absent.

## 3. The service's own configuration

Separate file, because it changes for different reasons and holds no
per-collector detail.

```
/etc/system-explorer/service.json
```

```json
{
  "schema": 1,
  "socket": "/run/system-explorer/api.sock",
  "budget": { "sharePercent": 1.0, "floorSeconds": 30, "ceilingSeconds": 900 },
  "hub": { "url": "wss://hub.example.internal/agents",
           "clientCertificate": "/run/secrets/se-client.pem" },
  "history": { "path": "/var/lib/system-explorer/history.db", "retentionDays": 30 }
}
```

`budget.sharePercent` is the share of **one core** the whole fleet may hold. The
service derives each collector's interval from its measured cost against that
number. It is a ceiling and never a target: a host inside its budget is swept at
the collectors' declared freshness and no faster.

`hub` is optional and the service must work fully without it. A host reachable
by nobody but its operator stays completely usable — that is the invariant the
whole federation design rests on, and a hub block that fails to connect must
degrade to *no hub*, never to *no observation*.

## 4. Confinement, if the service confines

A collector is a separate process, so the service *can* confine it — `ReadOnlyPaths`,
`PrivateNetwork`, a seccomp filter — rather than trusting it.

If it does, `readPaths` in the manifest is what the deployment declares, and it
should be **derived from the collector's own declaration rather than written by
hand**: `--declare` already has to name the paths the collector reads, because
the reference-command lint needs them. A deployment that hand-maintains a second
list will drift from the first, and the drift will present as a collector that
mysteriously cannot read something.

Recommended: generate `readPaths` from `--declare` at build time, and let the
deployment override only to *narrow*.

## 5. Ordering and readiness

- The manifest may be written before the collectors' store paths exist only if
  the deployment is atomic. In Nix it is.
- The service **re-reads the manifest on `SIGHUP` and on file change.** A deploy
  that adds a collector must not require a restart, because a restart drops
  every watch and loses the snapshot baseline.
- A collector named in the manifest whose `exec` does not exist is an **error
  fact**, not a silent omission — it is a deployment that half-happened, and
  that is worth seeing.
- A collector removed from the manifest stops being invoked. Its objects then
  vanish from the graph, which is indistinguishable from the subject going away
  unless the service says which happened. **It must say which.**

## 6. What the NixOS module writes

Sketch, not a proposal for the option names:

```nix
services.systemExplorer = {
  enable = true;
  budget.sharePercent = 1.0;

  collectors.units.enable = true;

  collectors.docker = {
    enable = true;
    socket = "/var/run/docker.sock";
    # the module adds the group; nothing else on the host gains it
  };

  collectors.servarr = {
    enable = true;
    instances = [ "radarr" "sonarr" ];
    environmentFile = config.sops.secrets.se-servarr.path;
  };
};
```

The module's job is to turn that into the two files above, to materialise
nothing secret into the store, and to **fail the build** when a collector is
enabled without the authority it needs — a missing `socket`, a missing
`environmentFile` for a collector whose declaration says it requires one.

That last check is only possible because `--declare` states what a collector
requires. It is the same argument as `readPaths`: the declaration is the single
source, and the deployment is generated from it rather than kept in step with it.

## 7. What this does not decide

- **Whether a collector is resident or run-and-exit.** That is the collector's
  own declaration and the service's scheduling, not the deployment's business.
- **Which collectors exist at all.** Shipping one costs a file on disk; the
  deployment decides authority, not interest.
- **The wire format between service and collector.** Specified separately.
- **How secrets get onto the host.** `sops-nix`, agenix or a hand-placed file —
  the manifest only ever names a path.
